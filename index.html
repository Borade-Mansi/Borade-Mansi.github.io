How I triage an alert

Illustrative triage ticket: SSH brute force then successful loginHIGH
1 ValidateFour failed SSH logins in 5 seconds, then a success from the same source. The usernames differ (root, admin, ubuntu, test), so this is not a user typo.
2 ScopeHost: Ubuntu SSH target. Source: 10.0.0.5. Window: 09:14:02 to 09:14:09. Accounts tried: root, admin, ubuntu, test.
3 EnrichIn my lab the source is the Kali machine. On a real network I would check IP reputation, geolocation and what else that source contacted.
4 ClassifyBrute force with a successful login (MITRE ATT&CK T1110). High severity because the attacker got in.
5 EscalateEscalate to Tier 2 with the evidence. Recommended actions: disable the compromised account, force a password reset, block the source IP, review activity after 09:14:09 and move SSH to key-based login.

AI security notes

My study notes on securing applications built on large language models, based on the OWASP Top 10 for LLM Applications (2025 edition). I'm putting them into practice in my AI security lab.

LLM01Prompt injection

Risk: Crafted text, typed by a user or hidden in a document or web page, overrides the model's instructions.

Defence: Keep system and user context separate, give the model least-privilege tools, filter inputs and outputs, require human approval for risky actions, and alert on repeated attempts.

LLM02Sensitive information disclosure

Risk: The model reveals personal data, secrets or proprietary data.

Defence: Keep secrets out of training data and prompts, redact outputs, and enforce access controls on anything the model can retrieve.

LLM03Supply chain

Risk: A compromised model, dataset, plugin or library enters the application.

Defence: Use trusted sources, verify hashes and signatures, pin versions and scan dependencies.

LLM04Data and model poisoning

Risk: Tampered training or fine-tuning data plants backdoors or bias.

Defence: Vet and version data, record where it came from, and test model behaviour before release.

LLM05Improper output handling

Risk: Model output is passed to another system unchecked, leading to XSS, SQL injection or code execution.

Defence: Treat model output as untrusted input: validate, encode and parameterise it.

LLM06Excessive agency

Risk: The model has too many tools, permissions or too much autonomy.

Defence: Grant the minimum tools and permissions, and require approval for high-impact actions.

LLM07System prompt leakage

Risk: Hidden instructions, or secrets placed in them, are exposed.

Defence: Never store secrets in prompts and enforce rules outside the model.

LLM08Vector and embedding weaknesses

Risk: A retrieval store (RAG) leaks data across users or is fed poisoned documents.

Defence: Use permission-aware retrieval, validate ingested content and monitor the vector store.

LLM09Misinformation

Risk: The model gives confident but wrong answers that people act on.

Defence: Ground answers in sources, show uncertainty and keep human review for important decisions.

LLM10Unbounded consumption

Risk: Huge or endless requests cause outages, large bills or model theft.

Defence: Set rate limits, quotas and input size limits, and monitor usage.

The SOC view

Log every prompt and response and send them to the SIEM. Alert when one user repeatedly tries to override instructions, sends encoded payloads or submits unusually long inputs. Map what you find to MITRE ATLAS, and run threat modelling (STRIDE) before an AI feature ships.
